# Nucleus V2: a costed architecture hypothesis

> **Historical and superseded.** This paper records an earlier architecture hypothesis. [`specification.md`](specification.md), especially its normative Chapter 17 grammar, defines the current Nucleus language. Requirements stated below belong only to this historical proposal.

## Status

This paper records an architecture hypothesis rather than current language requirements. It described the programming model that an implementation of that proposal would preserve, the budget boundaries it would measure, and the experiment intended to select the first compiler architecture. Other syntax details, bytecode encodings, stack layouts, and byte counts were left open pending implementation measurements.

Nucleus is the smallest safe, practical language intended for routine programming on the TEC-1. Its implementation starts bottom-up with a handwritten Z80 compiler. Self-hosting and bootstrap work are important uses, but they do not justify reducing the source language to a notation that is unsuitable for ordinary programs.

## Governing constraint

The Nucleus compiler core, including every constant table required while compiling, must fit in one 16 KiB bank or page. Code or tables placed in another bank do not make an oversized compiler core acceptable.

Other resources have separate budgets and may use other RAM or banks when the platform permits:

| Resource                  | Accounting rule                                                                                             |
| ------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Compiler core             | Count executable code and required immutable data together against the 16 KiB gate.                         |
| Writable workspace        | Report peak live bytes, including lexer, parser, symbol, lowering, and emission state.                      |
| Generated output          | Report emitted program bytes separately from compiler storage.                                              |
| Bytecode interpreter      | Give the VM its own code, constant-data, and writable-state totals. It may reside in another bank.          |
| Direct and later backends | Measure each backend independently and state whether it replaces or supplements another resident component. |
| Execution cost            | Measure representative instruction counts or cycles; do not fold speed into the compiler-size result.       |

For each tested compiler configuration, count the front end, its active emitter, and all constants they require against the compiler-core gate. A mutually exclusive or later backend may have a separate budget, but its placement must not hide code needed by the tested compiler.

The flat approximately 63 KiB address-space profile described in `../abstract-machine.md` may still govern other Lanternfly or Candlemoth experiments. It does not govern Nucleus V2. Treating TEC-1 banking as future work would postpone the constraint that this design exists to satisfy.

## Evidence and admission

Every size or performance claim must carry one of these labels:

- **Measured:** produced by an identified build or run, with the measurement method recorded.
- **Projected:** calculated from measured components under stated assumptions.
- **Hypothesis:** a design expectation that an implementation has not yet tested.

Do not present source-line count, host executable size, or an opcode sketch as a target byte count. Report ranges only when the assumptions that produce the range are explicit.

The minimum programming model in this paper is a requirement. Formal arguments, named local variables, support for a typed result, and the safe data forms below do not have to earn admission against a deliberately unusable global-register baseline. Only measurements showing that a required feature is infeasible may reopen that requirement. If a faithful implementation cannot meet the compiler-core gate, the architecture hypothesis has failed or needs redesign; silently deleting part of the programming model is not a successful result.

Apply the measured cost-versus-saving rule to optional conveniences and later expansion. For each optional construct, measure its incremental compiler-core bytes, constant data, peak workspace, interpreter or backend cost, emitted-program effect, and any reduction it permits elsewhere. Admit it only when that evidence justifies the total-system trade. Exclude optional syntax and machinery by default, then add one measured construct at a time.

## Minimum source-language model

Nucleus source should resemble a small, typed, structured BASIC. The first useful implementation must provide:

- scalar types `u8`, `u16`, and Boolean, including Boolean conditions and results;
- subroutines with formal arguments, named local variables, and one typed return result where a routine returns a value;
- fixed-size arrays with bounds-checked access;
- records whose field layout and offsets are fixed at compile time;
- bounded strings or string views whose accessible extent is known;
- assignment, calls, `if`/`elseif`/`else`, `while`, counted `for`, and `return`;
- static rejection of unsafe operations where the compiler has enough information, and checked operations that trap when safety depends on runtime values.

Except for spellings settled below, these are semantic requirements rather than a complete grammar. The first grammar should implement no more syntax than these requirements need.

The source language exposes neither raw pointers nor pointer arithmetic. After type checking, lowering may represent a fixed record or fixed-array alias as one address-sized word because its type supplies layout and extent. Open arrays, slices, and string views may require hidden address-and-length pairs; their first representation and return ABI remain open. Addresses and offsets belong to typed aliases, the IR, or a backend representation. A Nucleus program cannot fabricate them or manipulate them as integers.

Heap allocation, resizable strings, generics, exceptions and unwinding, arbitrary casts, destructors, `finally` or `defer` actions, variable-sized local allocations, advanced type machinery, and unrestricted dynamic data are outside the first design. Other familiar constructs remain candidates for measured expansion rather than assumptions in the initial compiler.

Recursion is not required in the first vertical slice. This is implementation staging, not a permanent language prohibition. A later recursion experiment must account for activation storage, call depth, re-entry of temporaries, safety checks, and failure behavior before an implementation commits to supporting it.

## Deliberate type-surface cuts

The V2 source type system excludes several complete mechanisms:

- Enumeration types are absent. Programs use named integer constants, and arrays have no enumeration-indexed domains.
- Subrange and range types are absent. Fixed arrays have zero-based indices and declared lengths; bounds checks provide the safety property without distinct range types or arbitrary lower bounds.
- Records have one fixed layout. Variant records, unions, and overlaid aggregate layouts are absent.
- Set types are absent. Programs that need a set representation use byte or word arrays and library routines.
- Address-bearing aliases and `u16` remain distinct source types even when the VM stores both in word-width slots. The source language admits no unsafe reinterpretation between them.

These cuts remove type categories, compatibility rules, layout cases, and lowering paths rather than trimming individual spellings. The relevant Oberon precedent is this method, not its exact feature set: Wirth removed whole mechanisms and later restored a constrained counted `for` because indexed traversal was common. Nucleus likewise retains one mechanically lowered counted loop while excluding type machinery that would create independent compiler paths. Historical precedent does not replace the size ledger.

## Front-end and lowering boundary

Compilation is streaming and single-pass. A declaration must precede its use unless an explicit forward signature supplies the name, parameter types, optional result type, and declared clobber set. This rule permits calls before a routine body without requiring a later global inference pass.

The front end type-checks names, calls, results, field accesses, indices, and string extents before it emits raw storage operations. Parameters and locals may then receive fixed virtual slots. Record fields and fixed-array elements may lower to typed base-and-offset operations; open array and string views may lower to hidden base-and-length values.

Lowering should regularize source constructs when doing so reduces downstream cases. A small vocabulary of typed semantic operations is preferable to carrying source-specific variations into every backend. This principle does not require the source programmer to write one operation per statement or to manage the compiler's temporaries.

## Static type metadata and aggregate aliases

Source variables and expression values are typed; virtual register storage carries no runtime type tag. The compiler may record that a variable of type `Person` occupies slot 3, but the slot itself has no permanent source type.

The compiler uses compact type IDs. Reserved IDs identify predefined scalar types, and each declared record and fixed-array type receives an ID. A symbol records its type ID, storage or virtual-register slot, and class flags. A routine signature records parameter type IDs, either no result or one result type ID, and its declared virtual-register clobbers.

The streaming expression compiler carries a value location and type ID. Local operations transform or check that pair:

- indexing a fixed array produces its element type;
- field selection produces the field type;
- a call expression takes its type from the routine signature;
- assignment and `return` check the value type against the destination or declared result.

This model requires neither an AST nor a global inference pass. Aggregate compatibility initially requires exact type-ID equality because V2 has no inheritance, variant layouts, or structural equivalence. Scalar conversions remain limited to forms the language explicitly admits.

An aggregate alias contains a runtime address and a compile-time referent type. Only the address is stored, passed, or returned; symbols, expressions, assignments, and routine signatures preserve the type ID. No runtime tag accompanies the address.

Records and fixed arrays are not returned by value or copied as routine results. An aggregate result is a typed alias to storage whose lifetime survives the call. Because local aggregate variables are aliases rather than owned aggregate storage, the language provides no local-frame aggregate that could escape through a return. Open arrays, slices, and views remain separate because their address-and-length representation may require a different result ABI.

## Structured control surface

General multi-way selection initially uses one flat `if`/`elseif`/`else` chain. `elseif` is one unhyphenated keyword, not the context-sensitive pair `else if`. The parser reads clauses in an iterative loop, and the complete chain has one `end`; a genuinely nested `if` has its own `end`.

An `if` used as the sole statement of an `else` has the same simple truth conditions as the flat chain. The dedicated `elseif` form remains because it gives clauses unambiguous scopes and terminators and avoids context-sensitive parsing. The iterative form is expected to reduce parser state; the compiler-core measurement must confirm the saving.

Pattern matching and general `select`/`case` are absent from the initial language. A restricted dense, nonnegative jump-table form may be reconsidered only if measured emitted-code savings pay for its compiler-core, table, and test costs.

V2 has `while` and one counted `for` production. It has no `repeat until`, `do while`, omission-based `for` variants, anonymous counters, implicit array-length bounds, `for in`, iterator protocols, range objects, or callbacks.

A counted loop names its counter and supplies start and destination expressions. `to` makes the destination inclusive; `until` makes it exclusive. The compiler evaluates both expressions once when the loop begins. An optional `step` is a nonzero compile-time signed constant and defaults to `+1`; it is compile-time control metadata, not a new signed runtime scalar type.

Positive steps use ascending comparisons and negative steps use descending comparisons. An initial counter already beyond the destination in the selected direction executes zero iterations. `step 0` is a compile-time error. The canonical traversal of a collection is zero `until` its length.

Both counted forms lower to ordinary counter initialization, comparison, conditional branch, body, increment, and backward branch operations. The VM has no `for` opcode. `to` and `until` differ only in the comparison emitted for their inclusive or exclusive destination.

Every loop supports unlabeled `exit` and `continue`, each applying to the innermost loop. `exit` branches after that loop. `continue` branches to a `while` condition or to the increment-then-condition path of a counted `for`. Their incremental grammar and lowering structure is limited to two statement forms, the current innermost-loop targets, and existing branch emission. The ledger must still record their exact compiler-core cost.

## IR as the semantic emission interface

The IR is primarily the contract between the checked front end and a backend. It is an operation vocabulary, not necessarily a stored intermediate file or in-memory graph.

The first implementation path serializes these operations as compact bytecode for a separate interpreter. A direct backend may instead consume the same operations as they are emitted and produce Z80 code without retaining an IR artifact. If interpretation loses on total cost, the type-checked operation boundary can therefore remain useful rather than being discarded with the bytecode format.

Structured source forms lower to comparisons, conditional branches, ordinary branches, calls, and returns. The semantic IR and VM need no dedicated `if`, `elseif`, `while`, `for`, `exit`, or `continue` opcodes. Address derivation remains distinct from `u16` arithmetic in the semantic operation set even if compact bytecode assigns both values word-width locations.

Keep this interface target-neutral where neutrality has no material cost against the TEC-1 constraint. A direct Z80 backend is the first comparison. Possible 6502 or x86-class backends are reasons not to embed Z80 accidents in the semantic operation set, but portability does not outrank the one-bank compiler-core gate.

## VM design hypothesis

The VM should first be easy and regular for the compiler to target. Compiler simplicity outranks VM execution speed. The bytecode must not inherit context-dependent Z80 exceptions. It is neither a clone of a historical processor nor an attempt to expose the Z80 through different mnemonics.

Candidate bytecode designs should prefer:

- a small number of uniform instruction families;
- consistent operand order and operand widths;
- predictable instruction lengths;
- explicit byte and word forms rather than context-dependent width;
- a regular call and result convention;
- checked indexing and other safety operations where centralizing them reduces total compiler code;
- structured call setup or region save and restore when these replace repeated front-end or generated-code machinery.

Source parameters and locals may map to fixed virtual slots. Any VM registers are memory-backed, untagged implementation locations, not source-language globals. They must not recreate the former `b` and `w` global arrays as the programming model.

This paper does not choose a pure stack machine, a register machine, or a hybrid. The present preference is for memory-backed virtual registers, with explicit stacks only where expression nesting, calls, or re-entry require them. The vertical slice must compare the code, tables, writable state, emitted output, and execution cost before fixing that choice.

PIC, TMS9900, AVR, RCA 1802, 6502, CHIP-8, and SWEET16 are useful precedents for operand regularity, interpreter structure, and compiler trade-offs. None is a compatibility target.

## Calls, storage, and safety

A routine declares either no result or one result type. A no-result routine uses bare `return`; a value routine uses `return` with an expression. V2 has no multiple results, assignment to the routine name, or implicit result variable. The current design permits an early `return`.

The VM ABI is all-caller-save over virtual registers with declared clobber sets, following the AZM-style model. Before a call, the caller saves live virtual-register values that overlap the callee's declared clobbers, places arguments, calls, captures any result before an overlapping restore, and then restores the saved values.

The same convention applies to recursion: the current activation saves its live virtual-register region around the recursive call and restores it afterward. The callee preserves no caller register state and requires no cleanup epilogue. Each `return` can place its result, if any, and immediately execute the VM return operation.

Direct return depends on the exclusion of destructors, `finally` or `defer` actions, variable-sized local allocations, and other scope-sensitive cleanup. The static rule that prevents a value routine from reaching its end without producing a result remains open; this paper does not require a mandatory final `return`.

Non-recursive fixed-size values may use statically assigned storage where lexical lifetime rules make that safe. Before recursion is admitted, the activation-region layout must provide distinct save storage for each call depth.

Bounds checking is part of array and bounded string semantics. Elide a check only when the compiler proves the access safe. Otherwise emit a checked VM operation, a checked helper call, or equivalent backend code. Record field selection uses compile-time layout and does not expose the underlying offset to source.

The source compiler should reject type errors, inaccessible storage operations, invalid constant bounds, and other statically knowable safety violations. It may stop at the first diagnostic in the initial implementation. Runtime bounds failures and similar dynamic safety failures may trap. Full exception handling and unwinding remain deferred.

## Native compiler machinery excluded from the primary path

The primary architecture avoids compiler features whose main purpose is producing hand-shaped native Z80:

- physical register assignment and spilling;
- irregular native operand constraints;
- instruction selection across Z80 special cases;
- short-versus-long branch selection;
- general relocation and link-time fixups;
- native stack-frame and calling-convention optimization;
- native peephole passes.

A direct Z80 backend may need a measured subset of this work. Its cost belongs to that backend comparison, not to the bytecode front end by assumption.

## Required vertical slice

Build one small program and the minimum compiler path needed to process it. The program must exercise:

- a subroutine with at least one formal argument;
- a named local variable;
- a typed return result and a call that consumes it;
- access to a record field;
- a bounds-checked fixed-array read or write;
- one bounded string or string-view operation;
- a flat `elseif` clause and a genuinely nested `if`;
- a counted loop and forward and backward control flow using the initial control floor;
- observable output.

Keep the program small enough that every emitted semantic operation can be audited. Include a call whose clobber set overlaps a live caller value, capture its result before restore, and exercise an early `return`. Add focused tests for inclusive `to`, exclusive `until`, positive and negative steps, a direction mismatch, one-time evaluation of bounds, and rejection of `step 0`. Exercise `exit` and `continue` in both loop forms, including a nested case that verifies the innermost-loop target. Cover a fixed-aggregate alias passed or returned without a copy. Add negative inputs for a type mismatch, an invalid field, an address/`u16` mismatch, an invalid aggregate result lifetime, and an out-of-bounds access not provable safe. These tests distinguish compile-time rejection from an emitted runtime trap.

For the bytecode path, report:

1. compiler-core code and required constant bytes against the 16 KiB gate;
2. peak compiler writable workspace;
3. bytecode interpreter code, constants, and writable state;
4. emitted bytecode size;
5. execution instruction count or cycles under a stated method;
6. the semantic-operation trace that produced the bytecode.

If practical, feed the same semantic-operation trace to a direct Z80 backend. Report that backend's resident bytes, peak workspace, emitted native size, and execution cost under the same workload. Do not infer a winner from host-language implementation size or from an unimplemented opcode table.

## Decision gate

The slice decides whether compact bytecode plus a separate interpreter is the first implementation architecture. Compare it with direct emission on total resident components, the hard compiler-core result, writable pressure, output size, and execution cost. Record which result is measured, which is projected from shared measurements, and which remains a hypothesis.

Do not expand the language or settle the VM organization before this gate. After the gate, add optional constructs one at a time and retain each only after measuring its marginal cost and system-level saving. Required programming-model features may be staged within the slice implementation, but the decision report must show that the final measured path supports all of them.

## Open decisions for the slice

The experiment must resolve, rather than assume:

- stack, memory-backed register, or hybrid VM organization;
- slot widths, activation-region layout, clobber-set encoding, and save-set computation within the caller-save ABI;
- the first bounded-string representation and operation, including the result ABI for open views;
- the static rule that rejects a value routine when control can reach its end without a result;
- which checks and call operations belong in bytecode versus shared helpers;
- whether a direct Z80 backend is small enough to justify retaining alongside or instead of the interpreter;
- activation depth bounds and trap behavior before recursion can be admitted;
- whether a restricted dense, nonnegative jump-table statement pays for its compiler cost;
- exact component residency and overlays without moving compiler-core code or required constants outside the one-bank gate.

No source syntax, opcode encoding, or numerical saving in this list is settled by this paper. The implementation and ledger must supply the evidence.
