# Plan: program storage and implicit startup

Status: implemented by `b2799117`; retained as a historical design record
Date: 2026-08-10
Planning baseline: `5e0a7af3` plus the uncommitted segmented-output experiment

## Purpose

Nucleus must preserve the ordinary meaning of a program variable on ROM-based,
RAM-loaded, and hosted targets. A variable is writable runtime storage. When it
has an initializer, it has that value before `main`; when it has no explicit
initializer, it has its language-defined zero value.

The compiler and target adapter may establish those values differently on
different machines. Those mechanisms must remain implicit. A programmer must
not declare a second ROM object, write a manual copy, or call an initialization
routine to obtain the value promised by one variable declaration.

This plan records the design work that preceded implementation. It does not
amend the language specification or the Z80 runtime contract. The current
authorities and capacity ledger supersede its provisional measurements and
limits.

## Settled source semantics

The design review begins with these invariants:

- Every program `var` denotes mutable storage at its runtime address.
- An explicit initializer determines the value visible before `main`.
- A declaration without an explicit initializer receives its language-defined
  zero value before `main`.
- Named scalar constants require no runtime storage.
- Nucleus 0.1 has no read-only aggregate declaration. An initialized aggregate
  variable cannot be placed in ROM merely because source code happens not to
  modify it.
- No source call reaches the startup machinery, and its state is not
  source-visible.
- The removed `at` and `align` modifiers are not part of this design.

These rules apply equally to ROM targets, CP/M-style loaded programs, and the
proof adapter. A target mapping may change representation and startup work; it
may not change the value or mutability of a source object.

## Smallest artifact model

The proposed backend artifact has four logical classes:

| Class                 | Runtime role                                          | Image bytes            |
| --------------------- | ----------------------------------------------------- | ---------------------- |
| code                  | executable instructions and startup stub              | yes                    |
| read-only image       | immutable compiler-generated bytes                    | yes                    |
| initialized data      | writable runtime objects with explicit initial values | yes, at a load address |
| zero-initialized data | writable runtime objects with zero values             | no                     |

Initialized data has two addresses when a target requires them:

- the **run address**, where source operations read and write the variable; and
- the **load address**, where the initial bytes reside before startup.

The two addresses may be equal. A CP/M loader can place initialized bytes
directly at their run addresses. A ROM adapter instead stores them in ROM and
generates a copy from load address to run address.

Zero-initialized data has a run address and extent but no load image. Startup
clears the complete extent before source execution.

## Implicit startup

The compiler emits one startup stub into the ordinary code class. Its address
is therefore selected by the code mapping rather than by a separate source
declaration.

The stub performs the target-required subset of these operations in order:

1. establish runtime state required by the adapter;
2. copy each initialized-data image whose load and run addresses differ;
3. clear every zero-initialized data extent;
4. invoke `main`; and
5. translate successful return, unhandled failure, and traps through the
   existing runtime contract.

No source routine runs before step 4. A loader or reset vector enters the
startup stub, not `main` directly. Other externally callable vectors do not
repeat initialization; their environment must enter them only after startup
has completed.

The generated copy and clear operations use compile-time-checked addresses and
extents. They have no recoverable source-level failure path. A malformed target
map or an output-capacity failure is diagnosed before publication.

## Target manifest responsibilities

The source manifest continues to order source parts. Target layout belongs to a
separate adapter-owned description. The design review must settle the smallest
representation that supplies:

- code base and limit;
- read-only image base and limit;
- initialized-data run base and limit;
- optional initialized-data load base and limit;
- zero-initialized data base and limit;
- startup entry exposure; and
- any fixed vectors emitted by the adapter.

The description must support both mappings below without changing Nucleus
source.

### ROM mapping

Code, read-only bytes, and initialized-data load bytes occupy ROM image
segments. Initialized and zero-initialized variables occupy RAM. Startup copies
the initialized image and clears the zero-initialized extent.

### Loaded or CP/M mapping

The loader places code and initialized bytes at their run addresses. The
initialized-data load and run addresses are equal, so no generated copy is
needed. Startup still clears zero-initialized storage unless the adapter has an
equivalent, proved loader guarantee.

## Vector interaction

A vector is a target-layout entry that writes one `JP target` instruction at a
fixed address. It does not move the current code cursor or alter the placement
of source declarations.

The reset or program-entry vector targets the generated startup stub. An
ordinary vector may target a previously declared routine only when the routine
has no parameters, no result, and no recoverable failure. Such a vector enters
the routine directly and never repeats program initialization.

Whether vectors are written in the target manifest or another adapter file
remains a design question. They must not reintroduce general source-level
address placement through another spelling.

## Publication and validation

Publication covers every image-bearing segment and all reported run extents as
one transaction. Before publication, the compiler or adapter verifies:

- every base, limit, cursor, load address, run address, and mathematical end;
- non-overlap within each physical address space;
- code and startup branch or call fixups;
- complete initialized-data and zero-initialized extents;
- the startup entry and every vector target; and
- every output and manifest capacity.

A failed compile leaves the previous published artifact unchanged. Tests must
make tentative code and data bytes differ from the previous publication before
forcing a late failure; comparing identical images does not prove rollback.

## Open design decisions

The design is not settled until review answers these questions:

1. Does one initialized-data load/run pair suffice for the first adapter, or
   must the manifest admit a bounded list of copy records immediately?
2. Does the adapter report vectors in the same segment table or in a separate
   bounded table whose bytes still participate in atomic publication?
3. Which startup operations are fixed compiler output, and which are supplied
   by a target-specific prefix or runtime entry?
4. May an adapter omit BSS clearing when its loader contract proves equivalent
   zero initialization, and how is that choice recorded and tested?
5. Which address spaces are compared for overlap on machines with physically
   separate ROM and RAM, banks, or overlays?
6. What is the minimal address-tagged output report needed by Intel HEX and the
   existing D8 segment map?

Each answer must be stated as a checkable contract. Convenience alone is not a
reason to expose load images or initialization calls in Nucleus source.

## Design and review sequence

1. Reconcile this plan with the language specification's initialization rules
   and Sections 2, 4, and 9 of the Z80 runtime contract.
2. Define two complete example mappings: one ROM target and one CP/M-style
   loaded target.
3. Trace startup, normal termination, unhandled failure, and trap paths for
   both mappings.
4. Specify the bounded manifest fields, capacity diagnostics, overlap rules,
   and atomic-publication boundary.
5. Obtain an adversarial design review focused on programmer-visible
   initialization, load/run address confusion, vector entry, rollback, and
   cross-target equivalence.
6. Revise until the language specification, runtime contract, manifest model,
   and examples agree.
7. Obtain explicit project-owner approval before treating the result as an
   implementation task.

## Implementation gates after approval

Implementation should proceed in independently measured steps:

1. retain the existing single-image behavior as the degenerate mapping;
2. publish per-class segment metadata without changing program behavior;
3. emit initialized-data load bytes and the automatic copy path;
4. emit zero-initialized extents and the automatic clear path;
5. add the loaded-target case in which load and run addresses coincide;
6. add vectors only after startup entry is proved;
7. prove multi-segment rollback with deliberately different tentative bytes;
8. run correctness review, measured compression, and final correctness-and-size
   review before commit.

Every step reports compiler code, immutable data, core, workspace, each output
segment, runtime, instruction count, and T-states separately. The 16 KiB
compiler-core gate remains binding.

## Historical implementation evidence

The original segmented-output experiment demonstrated that one code segment,
one read-only/load-image segment, initialized RAM, zero-initialized RAM, an
implicit copy-and-clear startup stub, and transactional rollback fit within the
existing architecture.

Its latest executable Stage 7 measurement is 14,300 compiler-code bytes plus
390 immutable bytes, or 14,690 bytes of compiler core. Workspace is 2,564
bytes, selected runtime is 657 bytes, and the proof executes 1,359,658
instructions in 12,670,276 T-states. The proof includes exact 1 KiB boundaries
for initialized data and BSS. Individual aggregate objects were then bounded
at 255 bytes; four 255-byte strings plus a four-byte tail distinguished each
total region boundary. The later 16-bit aggregate-extent correction supersedes
that object limit. These figures remain historical measurements, not current
target budgets.
